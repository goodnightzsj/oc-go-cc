# 平台可靠性修复与 CommandCode 独立接入

## Goal

修复上一轮审查确认的全部功能/数据问题；核实并融合有价值的上游提交；完整适配 OpenCode Go、OpenCode Zen、AWS Bedrock、OpenRouter、CommandCode 的配置、路由、日志、独立平台统计与套餐展示；核实 Codex 和 Claude Code 的使用方式。按 2026-09-11 最新要求，完成并验证后提交推送、SSH 部署测试，之后才分析各页 UI/UX 美化。

## CommandCode 接入依据（2026-09-10 用户追加）

- 最新顺序：先查 CommandCode 官网/API 文档，分别判定 Codex 和 Claude Code 的原生调用支持。支持的协议直接接入官方端点；只有不支持的链路才参考 https://github.com/MAXeaglet/commandcode-proxy 实现反代转换。官方未记载不等同于已证实不支持，须记录证据缺口。
- 核对 CommandCode 的认证、模型映射、流式/非流式、工具调用及 usage；独立平台配置必须贯通加载、校验、环境变量、CLI、注册、GUI 保存和统计归属。
- 分别验证 Codex 的 Responses 与 Claude Code 的 Messages 链路；按官方证据选择原生透传或必要转换。区分客户端直连官方（本地无流量日志）与经本项目直连原生API（保留本地日志/统计）；仅支持上游 Responses 不等于支持 Codex 客户端。
- 日志、套餐查看、统计与独立平台设置仍是必交付，不因采用原生接入而移除；只接有正式合同的套餐/账单查询，明确区分官方账单、本地估算、未提供能力。
- 不执行参考项目的安装脚本，不导入真实凭证，不覆盖用户 Codex / Claude Code 全局配置；参考源码的采纳与未采纳项保留来源及理由。

## Non-Goals

不更换技术栈，不读取或输出真实凭证，不修改用户全局客户端配置，不绕过平台套餐权限，不虚构账单/额度接口。部署阶段仅操作本项目已确认的远端服务；部署前不执行视觉重设计，部署后 UI/UX 阶段仅分析、不擅自实施美化。

## Constraints

- Go 现有依赖与原生 HTML/CSS/JS；先复用现有转换与配置逻辑。
- 兼容已有四个平台及配置；未知状态不模拟成功或零消费。
- 主代理负责设计、整合和验收；子代理默认只读，仅明确限定的文件可受限实施，不重叠写入。2026-09-11 恢复后旧写入授权失效，新的范围通过明确消息分配。
- 测试 HOME/DB 隔离，HTTP 上游使用 httptest；源码外的编译/分析缓存只用临时目录。

## Risks

跨平台记录归属、账单范围、配置/协议合同、旧数据库迁移、流式工具调用和上下游费用语义。详见 `.ai/preflight/risks.md`。

## Child Deliverables

1. 上游调查与安全测试基线。
2. 数据隔离与平台路由缺陷修复。
3. 官方文档优先的 CommandCode 独立平台实现及 Codex / Claude Code 链路，反代仅补足原生缺口。
4. 日志、套餐查看、统计与界面兼容修复。
5. 客户端文档与最终验证。
6. 提交、推送与既有 SSH 部署链路验收。
7. 部署后逐页 UI/UX 与数据呈现美化分析。

- 新平台接口由合成上游覆盖流式/非流式、工具调用、缓存 usage、认证失败与路由。

- 部署验收包括远端提交、服务健康和实际页面/API 行为；保留既有配置、数据库和回滚路径。UI/UX 分析发生在部署测试之后。
