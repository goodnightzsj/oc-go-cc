# 远端 OpenCode Go 历史数据消失诊断

## 结论（2026-09-11）

不是这次 UI 把记录隐藏，也不是 CommandCode 抢占了 Go 数据。现用数据库路径没有改变，`provider_usage` 原始账单仍有 **1390 条**；但历史、概览和分析读取的 `requests` 表已为 **0 条**。本轮首次部署前的备份也为0。

实际配置未设置 `storage.retention_days`，因此启用默认 **7天**。服务启动及每小时都按 `created_at` 删除过期 `requests`，不清理 `provider_usage`。旧备份的1390条记录全部满足此清理条件。这是能够解释当前状态、且仍在生效的原因；现存日志不能证明具体是哪一次清理执行，不能虚构精确删除时刻。

## 调用链与问题

1. [默认配置](../internal/storage/database.go:51)为7天；[服务启动](../internal/server/server.go:79)合并配置并启动清理器。
2. [清理器](../internal/storage/retention.go:44)启动即执行，之后每小时运行；[删除条件](../internal/storage/retention.go:67)为 `created_at < cutoff`，没有区分账单导入与本地请求。成功删除仅输出Debug日志。
3. [历史接口](../internal/gui/server.go:454)和[分析汇总](../internal/storage/analytics.go:105)只查询 `requests`。页面拉长时间范围不能恢复已经物理删除的行。
4. [Go账单同步](../internal/storage/provider_request_sync.go:308)可以重建缺失记录，但使用原快照时间作为 `created_at`；仅回填、仍保留7天规则，会再次被清理。
5. 当前“最近90天”等选项并不表示后台保存了90天记录，旧UI没有说明这一限制。这次重设计应改善空态与统计范围说明，但不修改事实数据来美化界面。

保留清理逻辑早于本次接入已存在；8月10日代码已有相同删除条件。不能把全量测试/服务健康通过当作历史数据非空或保留策略符合用户预期的证据。

另一个独立问题：Go官方额度查询返回403，表示上游拒绝当前Key的Go套餐权限；它与本地 `requests` 被清理不是同一条链路，不会因恢复旧账单而自动解决。

## 恢复边界与建议

当前只执行诊断，没有恢复或改保留配置。下一步如获明确授权，应先确定保留目标，备份现库，在隔离副本核对旧备份/原始账单与新Schema、价格来源、平台身份和去重，再事务式恢复必要行。不能直接用旧DB覆盖现库或盲目执行 `sync-requests --apply`。

- 备份能够保留当时已知的请求明细；原始账单通常只有时间、模型、Token和费用，不能补造成功率、延迟、路由和对话。
- 原始账单只覆盖8月6日的这份快照，不代表账户的全部历史。
- 若仍使用7天保留，回填旧 `created_at` 的数据会再次消失；调整策略属于额外配置/数据变更，需用户确认。
- 原始账单与展示请求不能无条件相加，否则会重复计数。

## 验证限制

SQLite均以`-readonly`运行；仅读取结构、计数、时间范围及所需聚合。没有触发迁移、VACUUM、账单同步、付费生成、AWS账单查询或服务重启。`journalctl`查询没有清理日志（退出1、No entries），因此删除的具体时间/操作者不可追溯。
