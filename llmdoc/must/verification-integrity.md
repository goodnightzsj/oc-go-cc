# MUST：验证完整性

声称"已验证"时不可协商的底线。2026-09-23 两次实际翻车后固定。

## 不可失败的测试

一条测试若在**缺陷存在**时也通过，它就没有验证任何东西——而且它比没有测试更危险，因为它会以"已覆盖"的身份阻止别人再去检查。两类实际发生过的失效：

### 注入必须证明注入生效

用改动源码来验证守卫测试（注入一个缺陷，断言守卫失败）时，必须先证明**文件字节确实变了**。

实际翻车：用 `str.replace` 注入，锚点字符串没匹配上，替换根本没发生，却输出了"注入成功"。那时测的是"未注入的代码没报错"，与守卫无关。换成正确锚点重做，守卫才如期失败。

- 注入后断言替换**前后文件不同**（长度、哈希或 `grep` 命中），再跑测试。
- 更稳的做法：让脚本在锚点未命中原样输出时**以非零退出**，而不是静默成功。
- 同理，任何"我先改坏它试试"的验证都要能区分"改坏了、守卫抓住了"和"根本没改成"。

### fixture 必须能区分正确与错误实现

排序、映射、分组、优先级这类断言，先问：**把修复删掉，这个 fixture 还会通过吗？**

实际翻车：给 History 的 Tokens 列排序写回归测试，2 行 fixture 里「插入顺序」「按时间排序」「按总 token 排序」三者恰好一致，所以删掉修复测试仍通过。换成 4 行、让三种顺序两两不同之后才有区分力。

- 构造 fixture 时先算出**正确实现的期望序**与**错误实现的期望序**，两者必须不同；相同就加行或换值。
- 断言要落在**显示的值**上，而不是某个恰好同向的代理指标——本项目判过头疼的一例就是表头按 A 排序、单元格显示 B。
- 覆盖判定边界：窗口类用左闭右开的两侧各取一点；阈值分档取「恰好等于阈值」与「阈值 +1」。

## 脱敏

- 脱敏正则必须覆盖**实际会出现的前缀**。只匹配 `sk-` 的正则对 `sk_` 前缀的 key 完全不生效——实际翻车过一次，明文 key 被打进了回复。
- 只匹配一种前缀的安全网等于没有。宁可**不打印**疑似凭证的字段，也不要依赖正则。
- 不确定某字段是不是凭证时，按凭证处理。
